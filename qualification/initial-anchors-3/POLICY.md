# Production-library dataset with at least three initial anchors

User-confirmed policy (2026-11-08): candidate libraries must be declared in the selected frontend manifest's `dependencies`; exclude `devDependencies` and peer-only declarations for every repository. For monorepos and documentation subprojects, use the actual selected frontend package manifest, not an unrelated repository-root manifest. Read this manifest from the pinned commit; retain submitted metadata separately when correcting its path. A library needs at least three distinct source functions in the initial POG function-anchor set, before propagation or model calls. Count repeated bundled copies of a source function once. Preserve the existing POG settings (at least ten own-body property operations; fingerprints unique in the selected supplied source-reference pool and in an individual target chunk).

Retain qualifying previously sampled production libraries first. Remove unqualified libraries and retry them against the retained pool; then scan the remaining declared production candidates in deterministic name order. A candidate is accepted only if it has at least three initial anchors and every retained library still has at least three. Stop at ten, or exhaust the candidate pool. If the scan retains fewer than five, an exact backtracking search checks all potentially qualifying production candidates for a compatible five-library subset. A partial subset that loses required anchors is pruned because adding references cannot restore uniqueness. If a five-library subset is found, fill toward ten with compatible candidates. Drop the repository only if no compatible five-library subset exists for these supplied inputs. The trial-count optimization is checked against the canonical matcher, including duplicate target chunks and cross-library fingerprint ambiguity. Recompute anchors in the final selected pool and independently assert every selected library meets the threshold.

Anchor computation receives only captured JavaScript and explicit source-reference JavaScript inventories, never one-to-one labels, source-map positions, recovered functions, or model outputs. Reference snapshots follow the existing experiment preparation protocol: all available candidate-library source texts retained in the saved source maps, deduplicated by library, package-relative path, and content hash; they are not a claim to index the complete installed package. The source snapshots are materialized as fixed reference inputs before POG matching. Reference attribution currently requires a candidate package name in the source-map node_modules/~ path metadata. Vendor maps without attributable package paths remain unresolved rather than being assigned by filename alone. Reference coverage and parse failures remain visible. Eligibility applies to these supplied inputs and does not prove semantic equivalence or exact version identity.

One-to-one ground truth is computed separately from the captured JS/maps using the existing reciprocal-body-mapped-v2 collector. Only pairs of the selected qualifying libraries enter the final organized dataset. No minimum ground-truth pair count or recovery-rate threshold is silently added.

The build/capture archive remains available for traceability. The final dataset has a separate entry point and an explicit inclusion/exclusion manifest; unqualified archive subjects are not members of that dataset.
