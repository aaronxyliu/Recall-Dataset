# Source-function eligibility policy

Current user instructions (2026-11-09): retain 3–10 declared production libraries per repository. Each selected library needs at least three source functions with at least ten POG features. No initial-anchor or source-to-bundle matching threshold applies. The same frozen POG counter is retained: ten own-body property-operation occurrences, with successful POG extraction.

Run the source-only check before starting a Docker build. Use the actual pinned frontend manifest and lockfile, excluding devDependencies and peer-only declarations. Retain eligible previously selected production libraries, then try remaining production candidates in deterministic order until ten qualify or the pool is exhausted. Unknown package versions, unavailable sources, and parse failures remain explicit; they are not proof that a library has no suitable functions.

Inspect implementation JavaScript shipped by each locked package, excluding bundled node_modules, declarations, tests, examples and fixtures. Count syntactically distinct source functions, deduplicating identical normalized function ASTs across distribution copies; no fingerprint uniqueness or target match is required. Save at least three source-function witnesses and exact source-file hashes per accepted library. The witness count is a lower bound when scanning stops after three. Workspace source packages come from the pinned Git commit. Existing independently captured source snapshots may establish the same lower-bound criterion when exact package resolution is unavailable.

After building, independently verify the page and archive the captured JavaScript, source maps and one-to-one pairs for the selected libraries. Missing or zero correspondences remain recorded and do not silently introduce an extra acceptance threshold. Build/page failures are technical unassessed cases, separate from source-function eligibility. The original build/capture archives and earlier anchor-policy results remain historical evidence.

Selection repairs (2026-11-09): explicit exclusions and preferred production libraries are recorded in `selection-overrides.json`. For zero-pair pages, prefer eligible production dependencies observed in captured maps over server/build-only or unloaded dependencies. This is a sampling preference, not a minimum-pair or initial-anchor acceptance test. DrawDB excludes `@dbml/core` at the user's request. PrimeNG uses its built library manifest (`packages/primeng/package.json`), whose production dependencies are exercised by the showcase; root development and Angular peer-only dependencies are excluded.

When a map strips package directories, `ownership.py` establishes ownership by exact source-content SHA-256 matches to the locked npm tarball, including original sources embedded in that package's own source maps. The ownership receipt records package/version, tarball SHA-256, member and embedded source path. No basename-only guess is accepted. The pair collector and independent span verifier check the source hash before accepting those labels.

Explicit repository exclusions are recorded in `excluded-subjects.json` and enforced by the build gate, organizer and standalone audit. `esbuild/okikio--bundlejs` is excluded at the user's request; its historical build/capture archive is retained.

Correspondence scope is additionally restricted to module dependencies under [the module policy](../module-dependencies/POLICY.md). This controls accepted pairs and map-reference snapshots separately from the unchanged source-function threshold. Global-only production libraries do not qualify as replacement module candidates.

Library multiplicity additionally follows the [full-runtime duplicate-library policy](../no-duplicate-libraries/POLICY.md). Duplicate copies in global/vendor inputs also disqualify the library even though those inputs are not scored. Replacement sources must pass the same original source-function threshold; source eligibility does not reinstate an initial-anchor requirement.
